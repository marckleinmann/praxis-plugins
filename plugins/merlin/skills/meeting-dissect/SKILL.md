# meeting-dissect · The requirement list

Read a word-for-word transcript. Produce a complete list, with receipts, of everything the
other party asked for, objected to, offered or constrained. Show it to the user. Nothing is
written from a meeting until this list exists and the user has approved it.

This skill exists because of a real failure. A client specified a test set of ten homes in
a recorded call. The transcript captured it. The recorder's AI summary dropped it, and every
follow-up was built from the summary. The client asked again four days later, got nothing
again, and ended the engagement. The transcript sat complete on disk the whole time and
nothing read it.

The rule behind it: **an AI-written meeting summary is never a source. The word-for-word
transcript is the only source, and every item carries its quote and line number.**

## What this is not

- Not a summary. A summary compresses. This lists everything, and completeness is the
  product.
- Not a decisions log. A decisions log holds commitments and actions. This also holds the
  things a log has no place for: a spec, a quantity, a grievance, an offer that was declined.
- Not for the other party. It is the user's working list. Anything sent to the other party
  is written from this list afterwards, and only after the user approves it.

## Step 1 · Get a real transcript

Walk these in order. Stop at the first one that gives you the actual words.

1. **Already on disk.** A `meeting_<date>_<slug>.md` in the project's `knowledge/meetings/`.
   Read its `## Transcript` section. A file that holds only a summary is not a transcript;
   keep going.
2. **The recorder's connector.** If the user's recorder (Granola, Fellow, Fathom, Otter,
   Wispr Flow or another) is connected, ask it for the transcript itself, paged to the end.
   Never ask it for its notes or summary, and if it returns a summary alongside the
   transcript, ignore the summary.
3. **Paste.** Ask the user to open the recording in the recorder's app, copy the transcript
   view, and paste it here. This works and it is faithful.
4. **Export.** Whatever transcript file the recorder will hand over: `.txt`, `.vtt`, `.docx`.
5. **Stop.** Tell the user no transcript could be found, which of the four you tried, and
   what each returned. Then go to "Fail closed" in Step 6.

**A paywall, a permissions error or an empty reply at step 2 is not the end.** It means go to
step 3. Never use the summary instead, and never work from memory of the call.

**Hard refusal.** If the only text available is a recorder's summary, AI notes, highlights,
suggested action items, or a summary another Claude session wrote, this skill does not run.
Say so plainly and stop. There is no override.

Before going on, confirm it really is a transcript:

- More than one speaker label appears, or the meeting truly had one speaker.
- The length fits the meeting. Four lines for a 45-minute call is a partial capture: say so
  and keep walking the list above.
- If it looks cut off (ends mid-sentence, no closing exchange), go on but mark
  `coverage: PARTIAL` and say which end is missing.

## Step 3 · Extract, by category

**Read `extraction-prompt.md` (beside this file) first.** It is the extraction instruction,
and the second reading in Step 3B uses the same file, so both readings follow the same rules.

Read the transcript start to finish. For a very long transcript you may split it into
segments and have helpers extract each one, but the merge must keep every item. Never
re-summarize what a helper returned. A lower item count after a merge is a bug.

| Tag | What it captures | Why it is here |
|---|---|---|
| `ASK` | A deliverable requested. Capture **quantity, format, medium, orientation** when stated. | "Ten homes" and "one image, not a PDF" are exactly what summaries drop. |
| `SPEC` | A technical, design or business fact the work must respect. | |
| `PRIORITY` | The other party ranking something: "the number one thing", their biggest problem, why they took the meeting. | The stated top priority decides the deal. |
| `OBJECTION` | A grievance, doubt or complaint, including about work already delivered. | |
| `OFFER` | Something offered by either side: money, time, scope, a second project. **Record whether it was accepted, declined or left open.** | A declined offer has no place in an action list, so it disappears. |
| `CONSTRAINT` | A budget ceiling, deadline, hard no, tooling limit. | |
| `COMMITMENT` | Who owes what, by when. Both directions. | |
| `OPEN` | A question raised and not settled in the call. | |
| `DECISION` | Something actually settled in the call. | |
| `RISK` | A stated fear, or a bad past experience they are comparing this to. | |

Every item takes this shape:

```
- [ ] `<TAG>` **<one-line statement of the item>**
      ID: <meeting_date>#<nn>
      Quote: "<their exact words, trimmed only at the edges, never paraphrased>"
      Line: <n> (or <n>-<m>)
      Quantity/format: <literal values if stated, else "not specified">
      Status: <open | fulfilled | declined | withdrawn | superseded>
      Repeats: <count within this transcript>
```

**Rules.**

- **Word for word or nothing.** The quote is the speaker's actual words, filler included. If
  you cannot quote it, the item does not exist. Never infer an intent and file it as a
  requirement.
- **Literal quantities.** "Ten" is ten. "One image, not a PDF" is one image and a ban on
  PDFs. Never turn a number into "several" or a format into "a sample".
- **Both directions.** The user's commitments and declines count as much as the other
  party's.
- **A decline is an item.** When one side offers and the other says no, that is an `OFFER`
  with `Status: declined` and both quotes. It is the most expensive item to lose.
- **Do not merge near-duplicates.** Two askings of the same thing are one item with
  `Repeats: 2`. Two different asks that sound alike stay separate.
- **A long turn holds several items. Split it.** Citing a turn once does not mean everything
  in it was captured. Before moving past any turn of 60 words or more, list its distinct
  claims and test each one.
- **IDs follow list order**, `<meeting_date>#01`, `#02` and so on. Never reorder an existing
  list, because the carry-forward step and the checker match on IDs.
- **A closed item that comes back is a new item.** Check the Closed sections of earlier
  lists for this client. When the client raises a closed item again, write a new item with
  its own ID and a `Reopens: <old ID>, closed <date>` line, and count the earlier askings in
  `Repeats`. The old ID stays closed.

## Step 3B · A second, independent reading

One reader misses things without anyone noticing. A second reader who never sees the first
list misses different things.

1. **Write the first list** to the Step 6 path with `second_pass: PENDING`.
2. **Start one helper in a fresh context**, on the same model as this session, never a
   smaller one. Give it only three paths: `extraction-prompt.md`, the transcript, and its
   output file `<merlin-data>/<Project>/updates/dissect-work/<YYYY-MM-DD>_<slug>/pass-b.md`.
   Tell it not to open any `dissect_*` file and not to start helpers of its own. Never give it
   the first list, a digest of it, or this conversation.
3. **Compare the two readings:**
   `python3 <scripts>/diff_passes.py <first list> <pass-b.md> --transcript <transcript>`
4. **Add, never filter.** Every item only the second reader found, whose quote checked out
   against the transcript, goes into the list under `### Found by the second reading only`,
   with its own ID and `Status: open, flagged: second reading only`. An item whose quote was
   NOT FOUND in the transcript is not added; note it in the coverage note. Items only the
   first reading found stay. Every one-sided and POSSIBLE match is shown in Step 7.
5. **Stamp** `second_pass: COMPLETE` and `pass_diff: a_only <n> · b_only <n> · possible <n> ·
   unverified <n>`.

**If this session cannot start a helper**, stamp `second_pass: DEFERRED (no helper
available)` and say so plainly in Step 7. The list is then one reader's work, and the user
should know that before approving it. Offer to run the second reading in a fresh session.

## Step 4 · Rank by repeat count, then by stated priority

1. Anything tagged `PRIORITY` where they said it matters most.
2. Everything with `Repeats: 2` or more, highest count first.
3. `ASK` and `SPEC` items with literal quantities or format bans.
4. Everything else, in transcript order.

**The repeat count is the most valuable signal here.** A client who says the same thing five
times is telling you what the decision turns on.

## Step 5 · Carry forward from earlier meetings

Earlier lists for the same client live beside this one:
`<merlin-data>/<Project>/knowledge/meetings/dissect_*.md`.

**Run the script. Never pick carried items by reading.** Reading by meaning drops whole
categories: an objection, a constraint or a spec can never be "fulfilled", so a reader
looking for unfinished work skips them.

```
python3 <scripts>/carry_forward.py --dir <merlin-data>/<Project>/knowledge/meetings \
  --before <meeting_date> --client "<this list's client: value>" [--exclude <this list's path>]
```

It finds the latest earlier list for this client (`--client` is required when one project
folder holds several clients, and the script refuses without it) and prints every earlier
item, whatever its tag, in three sections, each item with its `ID:`:

- `## Still open from prior meetings`: owed work. ASK, OPEN, RISK, COMMITMENT, open OFFER.
- `## Standing context`: facts that stay true until something changes them. OBJECTION,
  CONSTRAINT, SPEC, PRIORITY, DECISION, declined OFFER.
- `## Closed since last meeting`: items the earlier list had already closed.

It refuses (exit 3) when the earlier list is not stamped `COMPLETE`, or when it reads fewer
items than that list says it holds. It skips an earlier list marked TRANSCRIPT-ABSENT or one
with no `client:` value, and says so (exit 4: the stamp here can be at most PARTIAL).

Paste its output at the top of the body and its frontmatter lines into Step 6. Then go
through it against this meeting:

- **Said again this meeting:** add a `Restated <meeting_date>:` line with the new quote and
  line. The item stays where it is and keeps its ID.
- **Closed this meeting:** move the whole block to `## Closed since last meeting`, set
  `Status:` to `fulfilled`, `withdrawn` or `superseded`, and add a `Pointer:` (what fulfilled
  it, the client's own words withdrawing it, or the item ID that replaces it). Update
  `carried` and `closed` in the frontmatter.
- **Never delete a carried block.** Standing context leaves only by `superseded` or
  `withdrawn`, with a pointer.

**An owed item asked twice and delivered zero times is a red flag**, shown 🔴 at the very top
of the file, with "asked N times, delivered zero".

**Check for meetings that were never listed.** Look through the project's whole `knowledge/`
folder for transcript files (a `## Transcript` section, or a dated meeting or transcript file
name) and match each to a list through `dissect_of:` and the meeting date. Any transcript
with no list counts as not listed; when in doubt, it counts. `carry_forward: COMPLETE` is
allowed only when nothing is unmatched AND `validate.py` exits 0 (Step 6). Otherwise the
stamp is `PARTIAL` with the count, and Step 7 offers to list the older meetings.

## Step 6 · Write the list

Path: `<merlin-data>/<Project>/knowledge/meetings/dissect_<YYYY-MM-DD>_<slug>.md`

```yaml
---
dissect_of: <path to the transcript file>
meeting_date: <YYYY-MM-DD>
client: <name>
source: <recorder connector | pasted | export>
provenance: VERBATIM        # or TRANSCRIPT-ABSENT
coverage: FULL              # or PARTIAL, with a note
item_count: <n>              # this meeting's items
prior_dissect: <path printed by carry_forward.py, or none>
prior_items: <N>             # every item of the earlier list
carried: <C>                 # Still open + Standing context
closed: <K>                  # Closed since last meeting
carry_forward: COMPLETE      # or PARTIAL, or DEFERRED (with the reason)
carry_forward_basis: computed <date> against <n> earlier lists; <m> earlier transcripts not listed
second_pass: COMPLETE        # or DEFERRED (<reason>)
pass_diff: a_only <n> · b_only <n> · possible <n> · unverified <n>
turn_coverage: uncited <n> · under_extracted <n> at 60 words per item
---
```

**Run the checker before writing `COMPLETE`:**

```
python3 <scripts>/validate.py <this list>
```

Exit 0 means every earlier ID is carried or closed exactly once, every closed item has a
pointer, and `prior_items = carried + closed`. Exit 1 means the stamp may not be `COMPLETE`:
fix the file, never the stamp. Exit 2 means the file lacks the three carry-forward sections.

Body order: the 🔴 red flags, `## Still open from prior meetings`, `## Standing context`,
`## Closed since last meeting`, then `## This meeting` with the ranked list (and
`### Found by the second reading only` when Step 3B added items), then `## Coverage note`.

### Fail closed, and visibly

If Step 1 reached "Stop" and no transcript exists, write the file with
`provenance: TRANSCRIPT-ABSENT` and this as the first line of the body:

> **⚠️ TRANSCRIPT-ABSENT.** No word-for-word transcript could be found for this meeting.
> Nothing below has a receipt. Nothing sent to anyone may be written from this file.

Then list which of the Step 1 routes were tried and what each returned. Never fill the list
from memory or from a summary. An empty list with receipts beats a full one without them.

## Step 7 · Show the user

This is the step the whole skill exists for. The user sees the list **before** anything is
written from the meeting.

First, if `second_pass` is `PENDING`, run Step 3B now. Then run the coverage report:

```
python3 <scripts>/coverage.py <transcript> <this list> \
  --operator-label Me --operator-label Microphone --operator-label "<the user's name as the transcript labels them>"
```

Pass every label the transcript uses for the user, because a passed list replaces the
default. The user's name is in `<merlin-data>/ABOUT-ME/about-me.md`; ask if the transcript
labels them differently. The report lists every turn of 30 or more words by the other party
that no item cites, and every cited turn with 60 or more words per citing item, each with its
text. Record the two counts in `turn_coverage:`.

Show, in chat:

1. Red-flag items first, 🔴, with "asked N times, delivered zero".
2. **This meeting's list, every item, one line each, quote included.** Never a digest, a
   top ten, or "plus 20 more": the user can only spot a missing item in the complete list.
3. **Every earlier item this meeting touched**, in full: each one said again, and each one
   this meeting closed.
4. **Untouched earlier items as counts:** one line per section with the count per tag, and
   the file path. Then ask: "<n> owed items from earlier meetings were not mentioned. Did this
   meeting settle any of them?" Show any section in full when asked.
5. The comparison of the two readings: every item only one reading found, every POSSIBLE
   match, and every quote that was not found word for word.
6. The coverage report, every flagged turn with its text.
7. The carry-forward arithmetic, `prior_items N = carried C + closed K`, and the checker's
   result.
8. The coverage note.
9. The question: **"Anything missing or misread? Every flagged turn above needs a yes or a new
   item. Okay to save the corrected list?"**

The user can correct an item, add one, or mark one irrelevant. Apply the corrections, then
re-run `validate.py` and `coverage.py` before anything else reads the file.

**Never skip this step because the list looks clean.** The failure this skill prevents is a
workflow deciding on the user's behalf that it captured enough.

**A quote is a receipt. A judgement about tone is a reading, and it is labelled one.** A
transcript keeps the words and loses sarcasm, pacing and tone, and recorders mishear words.
Never state a reading of anyone's conduct with a receipt's confidence. Ask the user how it
was said, or give the reading as one possible interpretation beside the quote.

## Step 8 · Hand off

The approved list is now the only source for anything written from this meeting: a
follow-up email, a proposal, a recap, a task. Whatever writes it reads the dissect file, not
the transcript alone and never a summary.

- When a later piece of work fulfills an item, set that item's `Status` to `fulfilled` and
  point at the work. That keeps the carry-forward honest.
- **Point later work at the whole file, never at a hand-picked list.** A handoff note or a
  brief names the dissect path and says to read all of it. A selection drops items, and the
  dropped item is invisible afterwards.
- Tasks that come out of the meeting go through `merlin:task-management`, after the user
  says which ones to add.

## Delivery check (`--check <draft>`)

"Check this draft against what they asked for" takes a draft (an email, a proposal, a
document) and the current list, and reports per item:

- **Fulfilled**, with where in the draft.
- **Missed**, with the quote and line.
- **Contradicted**: the draft does something they explicitly ruled out. A PDF when they said
  "not a PDF" is a contradiction, not a miss.

An `ASK` with a literal quantity is checked literally. Ten means ten; three is a miss, and
the report says "asked for 10, the draft has 3".

## Reconcile (`--reconcile <Project>`)

Repairs a client's lists when an earlier one is PARTIAL, has DEFERRED carry-forward, or is
written in an item shape the script cannot read. Triggered by "reconcile the meeting lists
for <Project>". It reads lists only, never transcripts. Run one at a time per project.

1. List every `dissect_*.md` in the project's `knowledge/meetings/`, sorted by
   `meeting_date`.
2. Walk them in date order, keeping a running set of open items. A file whose items are not
   in the Step 3 shape is rewritten into it first, one block per item with an `ID:`, quotes
   and lines unchanged. That rewrite changes shape, never content. At each file:
   - **Merge repeats.** An open item said again later keeps its first citation and adds up its
     repeat counts. Match on the statement plus the quote, never on the line number alone.
     Two different asks that sound alike stay separate; when in doubt keep both.
   - **Close what was answered.** An earlier open item answered by a later `DECISION` or a
     fulfilled item becomes `fulfilled` or `superseded`, with a pointer.
   - **Note what was answered earlier.** A new open item already answered by an earlier
     meeting's `DECISION` gets that pointer.
3. Rewrite each file's three carry-forward sections and 🔴 red flags from the running set as
   it stood before that meeting, starting from `carry_forward.py` output for that date.
4. Run `validate.py` on each rewritten file, then the Step 5 check for meetings never listed,
   and update each stamp: `COMPLETE` only where the checker exited 0, otherwise `PARTIAL`
   with the count.
5. Report how many files are COMPLETE, PARTIAL and DEFERRED. On any PARTIAL, name the
   transcripts with no list and offer to list them.

Reconcile changes only the carry-forward sections, the stamps, `ID:` lines, item statuses
with pointers, and the item shape of a file the script could not read. Statements, quotes
and line numbers stay as written. Transcripts are never touched.

## When things go wrong

- **Only a summary is available.** Refuse. Say which routes were tried. Do not run.
- **The transcript is partial.** Run, mark `coverage: PARTIAL`, name the missing end, and
  say so when showing the list.
- **Speaker labels are unclear** ("Speaker 1", "Microphone" with no names). Work out who is
  who from context and write the mapping in the coverage note. If it is genuinely unclear who
  asked for something, flag the item rather than guess: putting the user's own words in the
  client's mouth is the worst error available here.
- **`carry_forward.py` refuses.** The earlier list is PARTIAL or DEFERRED, or written in a
  shape the script cannot fully read ("parsed X of Y"). Run Reconcile, then try again. Only
  when that cannot be done, pass `--accept-partial`, name the gap in `carry_forward_basis`,
  and stamp this list PARTIAL. Never hand-pick the carried items instead. A "different
  clients" refusal means pass `--client`.
- **`validate.py` exits 1.** An item was dropped, duplicated, or closed without a pointer.
  Fix the file.
- **The transcript is not one turn per line.** `coverage.py` treats unlabelled lines as
  candidates and says so, and exits 2 on a file with no `## Transcript` section. When every
  line carries the same label, the report cannot leave out the user's own turns; read it
  knowing that.
- **Earlier meetings with this client were never listed.** The stamp is PARTIAL with the
  count. Say so, and offer to list the older transcripts: it is quick, and it often finds
  the unfulfilled item that is about to cost the deal.
